# Vertex Contract

Digital Contract by Vertex Studio · A Vertex Studio Product

Локальный проект сервиса контрактов: создание → отправка ссылки → данные и подпись получателя → закрытие → финальный PDF. Русский интерфейс, общие компоненты и дизайн-токены, Inter, светлая тема с акцентом `#635BFF`.

Supabase подключён через локальный `.env`: Auth и ключи проверены, пользователь применил подготовленную миграцию, наличие 10 таблиц и четырёх приватных хранилищ подтверждено через API. Публикация не выполнялась. Подключение GitHub и Vercel пользователь выполняет самостоятельно по [инструкции деплоя](docs/deployment.md).

## Запуск на Windows

Проверено с Node.js 24.18.0 и npm 12. Зависимости закреплены в `package-lock.json`.

```powershell
cd C:\Users\User\Desktop\digital_contract
npm.cmd ci
npm.cmd run dev
```

Откройте http://127.0.0.1:3000. При настроенном `.env` рабочее пространство требует входа. Без переменных Supabase доступен локальный просмотр без сохранения.

```powershell
npm.cmd test
npm.cmd run typecheck
npm.cmd run build
# При запущенном локальном сервере:
node scripts/smoke.mjs --configured
```

Для production-режима локально: остановите dev-сервер, затем `npm.cmd run build` и `npm.cmd start`.

Для проверки интерфейса без настроенных переменных Supabase запускайте `node scripts/smoke.mjs` без `--configured`.

## Что доступно сейчас

- Dashboard с поиском, фильтрами и честным пустым состоянием, без вымышленных контрактов.
- Создание из текста или трёх редактируемых шаблонов; заголовки, выделение, списки, реквизиты и предпросмотр.
- Импорт настоящего PDF/DOCX через локальный сервер. PDF сохраняет оригинальные страницы; DOCX преобразуется в редактируемый текст, без переноса исходного оформления.
- Общие экраны карточки, подписи, публичного приглашения и закрытого контракта; код адаптивных Desktop/Tablet/Mobile-раскладок.

Без Supabase изменения живут только в открытой форме. Перезагрузка страницы их удаляет; приложение предупреждает об уходе с несохранёнными изменениями. Сохранение, вход, отправка приглашений и финализация явно сообщают об отсутствии подключения. Нет подмены базы через localStorage или фиктивных успешных операций.

## Подключение нового Supabase-проекта

Текущий проект уже настроен. Этот раздел предназначен для переноса на другую базу; не применяйте начальную миграцию повторно.

1. Подготовьте отдельный проект, выбрав подходящее место хранения документов и персональных данных.
2. Примените `supabase/migrations/20261110061126_vertex_contract.sql` в SQL Editor нового проекта. Миграция создаёт таблицы, функции, RLS и приватные buckets. Для уже существующей базы сначала проверьте конфликты имён. Удаление/сброс базы не требуется.
3. Скопируйте `.env.example` в `.env.local` и заполните:

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLIC_KEY
SUPABASE_SECRET_KEY=YOUR_SERVER_SECRET
NEXT_PUBLIC_APP_URL=http://127.0.0.1:3000
```

Серверный secret key нельзя помещать в переменную с префиксом `NEXT_PUBLIC_`, клиентский код или репозиторий. `.env.local` исключён из Git.

4. В Supabase Auth включите Email/Password, настройте Site URL и разрешённый redirect URL `http://127.0.0.1:3000/auth/callback`. Для опубликованного приложения используйте его HTTPS-домен в обоих местах и `NEXT_PUBLIC_APP_URL`.
5. Перезапустите приложение. Создайте учётную запись и подтвердите адрес, если включено подтверждение email. Доставка писем зависит от настроек Supabase/SMTP.
6. Проверьте полный путь на тестовых данных: черновик → подпись создателя → ссылка в другом браузере → подпись получателя → закрытие → скачивание. Отдельно проверьте второго владельца, отзыв ссылки, истечение срока и повторные запросы. Полный браузерный сценарий ещё не проверен; результаты отдельных живых проверок Auth/Storage и SQL описаны в `docs/verification.md`.

## Устройство проекта

| Папка                                          | Назначение                                                         |
| ---------------------------------------------- | ------------------------------------------------------------------ |
| `app/(workspace)`                              | Dashboard, создание, загрузка, детали, шаблоны и настройки         |
| `app/sign`, `app/login`                        | Публичное приглашение и авторизация                                |
| `app/api`                                      | Проверка входных данных и прав, импорт, жизненный цикл, скачивание |
| `components/ui`, `app/globals.css`             | Общие компоненты, токены, адаптивность                             |
| `lib/domain.ts`                                | Статусы, типы и схемы валидации                                    |
| `lib/contracts.ts`                             | Supabase, хеши, файлы, подписи и финализация                       |
| `lib/pdf.ts`, `lib/documents.ts`, `lib/zip.ts` | PDF, DOCX и проверка загружаемых документов                        |
| `supabase/migrations`                          | SQL-схема, права, блокировки и серверная функция переходов         |
| `tests`                                        | Валидация, PostgreSQL, документы, HTTP и обработка сбоев хранения  |

Оригиналы, JSON-версии и финальные PDF хранятся отдельно. Версии находятся в `contract_versions`, файлы — в приватном Storage. Единственная функция изменения `vc_mutate` доступна серверной роли; владелец подтверждается сервером через Supabase Auth. Закрытый контракт и его содержимое защищены триггерами, а не только отключёнными кнопками. Это не защита от администратора, имеющего возможность менять саму схему БД.

Ссылки содержат случайный 256-битный токен во фрагменте URL; сервер получает его в POST, в базе хранится SHA-256. Срок приглашений и ссылок просмотра — 7 дней. Владелец может отозвать ссылки, в том числе после закрытия; уже выданные URL Storage живут до 60 секунд, скачанные копии отозвать невозможно. Получатель без регистрации определяется доступом к секретной ссылке, а не независимой проверкой личности. Не включайте запись тела таких запросов в инфраструктурные логи.

Номер `CTR-YYYY-000001` резервируется при закрытии и сохраняется при повторной попытке. Последовательность общая, не обнуляется ежегодно; пропуски при сбоях допустимы, цифры после 999999 не обрезаются. Итоговый PDF содержит данные и подписи сторон, номер и время; SHA-256 вычисляется по сохранённым байтам и проверяется при скачивании. Для PDF-оригинала добавляется отдельный лист подписания, исходные страницы сохраняются.

## Ограничения и оставшаяся проверка

- Загружаемый файл: до 4 МБ (лимит согласован с Vercel); PDF без пароля, 1–150 страниц; DOCX: до 40 МБ распакованных данных, 2000 записей ZIP и 100 000 символов текста. Изображения и исходная вёрстка DOCX не переносятся. В PDF поддержаны символы встроенного Inter Latin/Cyrillic; неподдерживаемый символ отклоняется перед подписью.
- Рукописная подпись — графическое подтверждение согласия, не квалифицированная ЭЦП. Шаблоны — редактируемые заготовки. Юридическая применимость и условия обработки персональных данных требуют отдельной проверки перед использованием с реальными клиентами.
- В журнале и подписях фиксируются серверное время, версия, сторона, согласие и User-Agent. IP-адрес пока не собирается: доверенный прокси и допустимый порядок обработки ещё не настроены. Узбекский и английский интерфейсы не реализованы.
- После неопределённого сетевого сбоя файл намеренно остаётся в Storage: удаление могло бы повредить ещё завершающуюся транзакцию. Также после удаления черновика могут остаться объекты. Фоновая сверка и удаление осиротевших файлов, сроки хранения, резервное копирование, ограничения частоты запросов и мониторинг нужны перед публичным запуском.
- Проверки PostgreSQL выполняются в PGlite с минимальными схемами Auth/Storage; они проверяют SQL, роли и переходы, но не заменяют интеграцию с живым Supabase.
- Браузерный host в рабочей среде недоступен. Визуальная проверка Desktop/Tablet/Mobile, управление пальцем и полная проверка пользовательского сценария в браузере не выполнены. HTTP-проверка не заменяет их.
